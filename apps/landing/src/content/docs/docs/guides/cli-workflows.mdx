Use the CLI yourself or let your coding agent run it. Start with an authoring project to change an app, or a writable `.slop` document to work with its data.

## Choose how to run commands

Install Bun 1.4.2 or newer and the hitSlop Mac app. The examples below use `bunx @hitslop/cli`.

| Entry point | When to use it |
| --- | --- |
| `bunx @hitslop/cli COMMAND` | Run the authoring CLI without a global install. |
| `slop COMMAND` | After `bun install -g @hitslop/cli`, with Bun's bin directory on your PATH. |
| `"/Applications/hitSlop.app/Contents/Helpers/hitslop-native" COMMAND` | Run native document commands directly, without Node or Bun. |

Use `bunx` or `slop` for the examples below. Build, register, and document commands use the installed Mac app, which can be closed. Browser preview works without it.

For an app installed under `~/Applications`, use `"$HOME/Applications/hitSlop.app/Contents/Helpers/hitslop-native"` in the native commands.

Append `--help` to any command to see its arguments.

## Create, preview, and register an app

```sh
bunx @hitslop/cli init weekend-kit
cd weekend-kit
bun install
bun run check
bun run dev
```

`init` asks what you want to build and who the author is. The agent you launch next sets the app's title, description, and categories in `manifest.json` to match what it builds; you can edit them there anytime. Your description is saved in `BRIEF.md` alongside the checklist starter and local agent guidance.

At the end, choose which agent CLI should build your slop. The picker offers detected Codex, Claude Code, Gemini CLI, and OpenCode installations. Choose **Other CLI…** for Grok or another installed tool: enter its executable name or path, then its prompt option (leave blank if it accepts a positional prompt). The agent opens in the new project and is asked to read the brief and hitSlop guidance before implementing your app. It uses its existing account, model, and permission settings.

Choose **Finish without launching** to work manually. If an agent fails or you cancel the launch, your project remains ready to use. No agent is installed automatically.

For an agent or script that is already running, create the project without another interactive session:

```sh
bunx @hitslop/cli init budget-book --yes \
  --brief 'Track spending by category with a monthly summary.' \
  --title 'Budget Book' --slug budget-book \
  --category finance --category personal --author Jordan \
  --description 'A simple monthly spending tracker.'
```

Flags set metadata explicitly; `--brief` and `--author` also skip their questions. `--yes`, CI, and non-interactive terminals never prompt or launch an agent. Missing values default to the directory name, `productivity`, `Anonymous`, and `A hitSlop mini app.`; an omitted brief uses that description. Metadata is validated before files are created, and an existing destination is never overwritten.

Read `manifest.json`, `AGENTS.md`, and `BRIEF.md` before editing. Preview data resets on refresh. Stop and restart the preview after source changes.

Stop the preview, then package the app and add it to your local catalog:

```sh
bun run build
bun run register
```

Build writes `dist/weekend-kit.slop`. Register builds it and adds it to the Mac app's template catalog. Existing documents keep their app version.

From outside the project, the equivalent commands take its source directory: `slop check ./weekend-kit`, `slop dev ./weekend-kit --port 5174`, `slop build ./weekend-kit`, and `slop register ./weekend-kit`. See [create your first slop](/docs/getting-started/) for the authoring tutorial.

## Create and open a writable document

In the Mac app, choose a template and select **Create**. For the terminal equivalent, run these commands from your authoring project:

```sh
"/Applications/hitSlop.app/Contents/Helpers/hitslop-native" create \
  --from dist/weekend-kit.slop --output "$HOME/Documents/Weekend.slop"
"/Applications/hitSlop.app/Contents/Helpers/hitslop-native" open \
  "$HOME/Documents/Weekend.slop"
```

Use the native commands above for `create` and `open`. Create makes a new document with the template's starting data; choose a destination that does not already exist. Open launches it in hitSlop.

## Read and edit data

In the remaining examples, replace `My.slop` with your writable document's path and quote paths containing spaces. Read `manifest.json`, the schema, and current data first:

```sh
bunx @hitslop/cli schema My.slop
bunx @hitslop/cli get My.slop
```

For a document with a text field named `title`:

```sh
bunx @hitslop/cli apply My.slop \
  --op '{"type":"set","path":["title"],"value":"Weekend"}'
bunx @hitslop/cli batch My.slop \
  --ops '[{"type":"set","path":["title"],"value":"Ready for the weekend"}]'
```

`apply` makes one edit. `batch` applies a list of edits together; if one is invalid, none are applied. Use row IDs from `get` when editing list items. See the [operation reference](https://github.com/hitSlop/hitslop/blob/master/docs/guides/cli.md#operations) for more examples.

Commands print JSON (edits print `{ids, sequence, value}`), and successful edits are saved. You can edit a document while it is open or closed. If a command fails and you are unsure whether the edit happened, run `get` to check before trying again.

## Move data between documents

There is no JSON import. To move data into a new document, create it from the template, read the source with `get`, and write the rows with one `batch` of `insert` operations. Give each insert an `id` so a retried command is refused as a duplicate instead of adding the row twice. Copy attachments with the commands below, then write their references.

## Change theme colors

```sh
bunx @hitslop/cli theme get My.slop
bunx @hitslop/cli theme set My.slop --values '{"accent":"#7050ad"}'
bunx @hitslop/cli theme reset My.slop --token accent
bunx @hitslop/cli theme reset My.slop
```

`theme get` reports defaults, overrides, and effective values. Set only tokens declared by the app. Reset one token with `--token`, or omit it to reset all overrides. The open window and subsequent captures use the changes. After an uncertain result, inspect `theme get` before retrying. See [styling](/docs/guides/styling/) for authoring theme tokens.

## Work with attachments

```sh
bunx @hitslop/cli attachments import My.slop ./photo.png
bunx @hitslop/cli attachments list My.slop
# Replace ATTACHMENT_ID with an ID returned by import or list.
bunx @hitslop/cli attachments export My.slop ATTACHMENT_ID \
  --output ./photo-copy.png
```

Import saves the file and returns its ID, name, type, and size. Ask your agent to store that reference in the appropriate document field so the app can use it. List shows saved attachment IDs and sizes.

Attachment export refuses existing output files and destinations inside the document package. After an uncertain import, inspect the attachment list before another command.

## Export PNG or PDF

```sh
bunx @hitslop/cli export My.slop --format png --output My.png
bunx @hitslop/cli export My.slop --format pdf --output My.pdf
```

Export saves your edits and prints the output path. Choose an output outside the `.slop` package; existing output files are replaced. Open documents export the current view. Closed documents use saved data and the app's starting view. See [icons and exports](/docs/guides/icons-and-exports/) for capture layouts.

## Install agent skills

Run the interactive installer to choose scope and agents:

```sh
bunx @hitslop/cli skills install
```

Or, from a project directory, install for all detected agents at project scope:

```sh
bunx @hitslop/cli skills install --all --scope project
```

Use `--scope global` to make the skills available across projects. Select skills once, then agents once. Installation only adds or repairs selected links; deselecting an item does not remove it. Bare `skills` is shorthand for `skills install`.

Repair existing links after updating the CLI package:

```sh
bunx @hitslop/cli skills repair --scope project
```

`skills repair` repairs existing links; `skills update` remains an alias. To install skills for a new agent, run `skills install` again. Installed links use a durable local copy, so clearing the bunx cache does not break them.

Remove installed links explicitly:

```sh
bunx @hitslop/cli skills uninstall --scope project
# Remove every installed hitSlop skill at this scope without prompts:
bunx @hitslop/cli skills uninstall --all --scope project
```

The guides copied into a project by `init` are ordinary files. Repair does not update them, and installation does not overwrite them without confirmation. Review those copies when upgrading your project.

## Upgrade the CLI

Install the compatible hitSlop Mac app before upgrading authoring packages. Within a project, update `@hitslop/cli` and `@hitslop/document` to the same released version; update `@hitslop/schema` to that version too if you depend on it directly. Continue using the project's `bun run` scripts. A global CLI update does not change a project's pinned dependencies.

If you use a global installation, update it with `bun install -g @hitslop/cli@VERSION`, replacing `VERSION` with the matching released version. Then run `slop skills repair --scope global` to refresh installed skill links. With bunx, use `bunx @hitslop/cli@VERSION skills repair --scope global` instead.

Interactive commands may show an update notice on stderr, checked at most daily. Network failures do not fail your command. CI and piped commands skip these checks; set `HITSLOP_NO_UPDATE_CHECK=1` to disable them in a terminal as well.
